## Контекст

Тренер і клієнти користуються телефонами в залі, часто без стабільного інтернету; акаунтів і хмари немає. Програма має потрапити на телефони за посиланням і лишитися робочою роки без супроводу.

## Рішення

Робимо веб-застосунок, що ставиться на головний екран (PWA): статичні файли, чистий JavaScript без фреймворку, без залежностей і без кроку збирання. Офлайн-роботу забезпечує service worker, який кешує всі файли. Розміщуємо на GitHub Pages.

## Чому

- **Нативний застосунок (магазини застосунків)** відкинуто: потрібні облікові записи розробника, публікація й оновлення через магазин, а клієнт мав би ставити програму через пошук у магазині, а не за посиланням з месенджера. Для одного тренера й кількох десятків клієнтів це непропорційно.
- **Фреймворк і збирання (npm-залежності)** відкинуто: через кілька років залежності застарівають і збірка ламається, а в проєкті нікому її підтримувати. Статичні файли можна покласти на будь-який хостинг і вони не «псуються з часом».
- **Сайт, що працює лише онлайн**, відкинуто: у залі інтернет не гарантований (історія 26 вимагає роботи в режимі польоту).

## Наслідки

- Кожен новий файл у `src/` треба вручну додавати в список кешу service worker і піднімати версію кешу. Забули, і на телефоні без інтернету відкриється зламана програма. Це вже одне з правил проєкту.
- Без збирання немає мінімізації й перевірки типів. Вся перевірка логіки лежить на тестах чистих модулів, а інтерфейс перевіряють руками.
- На iPhone браузерне сховище може бути стерте системою, якщо програму не поставлено на головний екран і не запитано постійне сховище. Тому «Зберегти копію» обов'язкова, а не додаткова.
- Автоматично відкрити файл з Telegram прямо в програмі PWA на iPhone не може. Це свідомо винесено за рамки: файл відкривається кнопкою.
- Усі шляхи мають бути відносними, бо GitHub Pages віддає сайт із підпапки.
- Публікація залежить від доступу до GitHub користувача і робиться окремим кроком після приймання.
